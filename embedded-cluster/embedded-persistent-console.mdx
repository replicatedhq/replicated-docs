# Persistent admin console (Beta)

This topic describes the persistent admin console for Embedded Cluster 3.x — an optional, always-on web UI for browser-driven upgrades and operations.

## Overview

The persistent admin console is an opt-in web service that runs on a controller node and exposes a dashboard at `https://<controller-hostname>:30080/console`. From the dashboard, end users can:

- View the currently installed application version and open configured application links
- Check application status
- See available updates, view release notes, and trigger an upgrade with a single click
- Upload air gap release archives directly through the browser (no SSH required)
- Generate a support bundle and download it for sharing with the vendor's support team
- View node status, generate commands to add nodes, and remove nodes from the cluster

All of this works without SSH access to the controller.

The persistent admin console is **not enabled by default**. To enable it, run `console install` on a controller node after the application is installed. See [Install the console](#install-the-console) below.

The initial application install and console setup require command-line access to a controller node. Once the console is running, end users can perform upgrades and configuration changes from the browser without command-line access.

:::note
For automated deployments (such as cloud marketplace offerings using cloud-init or user-data scripts), include `console install` in your provisioning script after the initial install completes. This gives end users browser-based access from first boot without any manual setup.
:::

### What enabling the console adds {#console-scope}

Installing and upgrading already happen in a browser. The installer serves a wizard that handles configuration, preflight checks, and the install or upgrade run itself, so an end user does not need a terminal for those steps. What the wizard does not do is stay available afterwards, because it belongs to an install or upgrade that someone started with a command on the host.

Enabling the persistent admin console adds a dashboard that is always there. From it, an end user can:

* Check the installed version and channel, and open application links
* Check application status
* See available updates and read release notes
* Upload an air gap release archive
* Generate a support bundle and download it
* View node roles and readiness, generate commands to add nodes, and remove nodes
* Start an upgrade, or change configuration values at the current version with **Redeploy**

Upgrades and configuration changes started from the console hand off to the same wizard, so the console does not duplicate it. The practical difference is that nobody has to be at a terminal to begin.

The console does not provide Kubernetes operations. There is no way to inspect or delete Pods, read container logs, or view Secrets from it, so those need command-line access to a node through [shell](embedded-cluster-shell).

If your end users need cluster-level visibility without command-line access, package a tool that provides it as a Helm chart extension in your application. See [Add Helm chart extensions](embedded-using#add-extensions).

## Install the console

Once the application is installed and running, install the persistent admin console on a controller node. The console serves its web UI from that controller's hostname.

1. On a controller node, run the install command:

   ```bash
   sudo ./<app-slug> console install
   ```

   Replace `<app-slug>` with your application slug.

1. (Optional) Use the `--port` flag to override the default port (`30080`):

   ```bash
   sudo ./<app-slug> console install --port 30443
   ```

1. Verify the service is running:

   ```bash
   sudo systemctl is-active <app-slug>-console-web.service
   ```

   The output should be `active`.

1. Open the console in your browser at `https://<controller-hostname>:30080/console`.

For the full set of flags, see [console](embedded-cluster-console).

### Choose a controller

The console can be installed on any controller node in the cluster. Replicated recommends running it on the primary controller — the first controller node installed in the cluster — because that node is typically the one users already access for cluster operations.

## Application links

If your release includes an `app.k8s.io/v1beta1 Application` resource with `spec.descriptor.links`, those links appear automatically on the console dashboard under **Open &lt;app-name&gt;**. No additional configuration is needed.

:::note
If you are upgrading from Embedded Cluster v2, any existing Application links carry over automatically.
:::

## Application status

The dashboard shows the application status that the Replicated SDK reports, along with the components that are not ready. The status displays only when the release includes the SDK. For how the status is calculated and how to control which resources are reported, see [Enable and understand application status](/vendor/insights-app-status).

## Support bundles

The console dashboard includes a **Generate support bundle** button that creates a support bundle directly on the host. Because the console runs as a systemd service on the host (not as a pod in the cluster), support bundle generation works even when the cluster is unhealthy or down.

The generated bundle is stored in the Embedded Cluster data directory. Ensure the filesystem hosting the data directory has sufficient free space for bundle generation. The data directory is also used for application images and persistent volume data, so large bundles on a constrained filesystem could impact available disk space.

After generation, the bundle can be downloaded from the console for sharing with the vendor's support team, or uploaded directly to the Vendor Portal from the console. See [Upload to the vendor portal](#upload-to-the-vendor-portal-beta) below.

### Upload to the vendor portal (Beta)

The console dashboard includes a **Share** button that sends a generated support bundle directly to the Vendor Portal, eliminating the need to download and share the bundle manually. After upload, the bundle is immediately available under the Troubleshoot tab in the Vendor Portal team account associated with the customer.

The **Share** button appears in the console only when all of the following are true:

* The customer's license has **Support Bundle Upload Enabled (Beta)** turned on. For instructions, see [Enable support bundle uploads](/vendor/support-enabling-direct-bundle-uploads).
* The installation is online. The button does not appear in air gap installations.
* The application includes the [Replicated SDK](/vendor/replicated-sdk-overview) version 1.17.0 or later as a chart dependency, and the SDK pod is running and reachable in the cluster. The console uploads bundles through the in-cluster SDK service, which exposes the upload endpoint starting in 1.17.0. If the SDK pod is unhealthy or unreachable, the **Share** button is hidden until the SDK becomes available again.

If any of these requirements are not met, the **Share** button is hidden and the bundle can still be downloaded from the console for manual sharing.

## Add nodes

Open **Nodes** in the console to see the cluster's hosts, roles, readiness, and internal IP addresses. Select **Add node**, choose one or more configured roles, and copy the commands that appear automatically. Run the generated download, extraction, and join commands on the new host. You need command-line access to the new host, but not to an existing controller.

The host list updates automatically while the node joins. There is no completion action in the console: after running the commands, you can navigate to another tab. A cluster with exactly two primary hosts is not supported; add another primary host. Adding primary hosts does not enable high availability automatically.

Join commands expire at the time shown below them. The console automatically refreshes expired commands while this page is open. Changing the selected roles automatically generates new commands for the new selection.

Adding nodes requires the **Multi-node Cluster** license field to be enabled in the license stored on the cluster. The **Add node** button remains visible but disabled when this entitlement is missing. If the vendor has enabled the field, open **License** in the console to refresh the cluster's license before adding nodes:

* **Online installations:** Click **Check for license updates**, then **Update license and deploy** when an update is available.
* **Air gap installations or online installations configured to use offline updates:** Select the updated license file from the vendor, then click **Upload license and deploy**. A release bundle is not required.

Both flows deploy the current application version with the saved configuration. If the updated license enables required configuration, complete it on **Config** before deployment. For more information, see [Multi-node license requirements](embedded-manage-nodes#requirement). To join nodes after refreshing the license, see [Join nodes](embedded-manage-nodes#add-nodes).

## Remove nodes

On **Nodes**, select **Delete** for a host. Review the warnings and select **Delete node** to confirm. The console uses the same removal routine as the `remove-node` CLI command: it drains healthy hosts, removes controller membership from etcd, cleans up the controller's autopilot ControlNode object, and deletes the Kubernetes Node object. Drain failure stops removal; force does not bypass a failed drain. NotReady hosts skip draining, as they do in the CLI.

The confirmation includes the CLI's controller-count warnings. When the CLI would require `--force`, the **Delete node** button stays disabled until you explicitly acknowledge **Force removal**. Force can bypass controller-count safety checks and, when cleaning up an already missing node, allow deletion of stuck Pods or orphaned PVCs. Deleting orphaned PVCs discards local data. Removing a controller can affect quorum and application availability; maintain at least three controllers for production HA.

A surviving, ready controller with the current cluster version executes the removal. It cannot remove itself, and the last controller cannot be removed through the console. To remove the last controller, run `reset` locally. The host serving your browser requests can be removed if another eligible controller can execute the operation; move the console or ensure another console is available before removing its host.

Only one console removal can run at a time across the cluster. The operation and progress are stored in Kubernetes, so refreshing the page or reaching another console instance does not restart the removal. If dispatch is pending, **Retry dispatch** sends the same operation to its assigned controller. The console does not transfer a running removal to another controller when it becomes unreachable. If the executing daemon restarts, the operation is marked failed; review the cluster state and current warnings before retrying. This shared removal state does not add load-balancer support to other console workflows.

Removal does not stop or reset the removed host. If it is reachable, run `reset` on it to clean up its local data before rejoining. If SeaweedFS is installed, follow the operator runbook's volume rebalancing procedures after removal. See [Remove a node](embedded-manage-nodes#remove-a-node).

## Recover or move the console

The console is hosted by a single controller. If the controller hosting the console is lost or the `<app-slug>-console-web.service` becomes unhealthy, rerun the install command on any controller node to bring it back up:

```bash
sudo ./<app-slug> console install
```

If the original controller is still healthy and you are recovering an unhealthy service, run the command on the original controller. If the original controller is lost, run the command on any other controller node. The console is stateless — the dashboard reads live data from the daemon, so moving it to a different controller is safe at any time.

## Uninstall the console

To uninstall the console from a controller:

```bash
sudo ./<app-slug> console uninstall
```

This stops and removes the `<app-slug>-console-web.service` systemd unit and frees the port. The cluster is not otherwise affected — the application continues running, and users can still upgrade with the `upgrade` command from the CLI. See [Perform updates in embedded clusters](updating-embedded).

## Limitations

The persistent admin console has the following limitations:

* The console can only be installed on a single controller node at a time. Reinstall on a different controller to move it.

* The console must be installed on a controller node; it cannot run on a worker node.

* The console can add and remove cluster members. Running join commands or resetting a removed host still requires command-line access to that host. Removing the last controller and enabling high availability require command-line access. See [Manage nodes](embedded-manage-nodes).

* The cluster must have TLS configured at install time. The console reuses the cluster's TLS certificate to serve HTTPS on its port.
