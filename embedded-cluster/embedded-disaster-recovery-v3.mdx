# Back up and restore Embedded Cluster v3

:::note Draft for release preparation
This page consolidates disaster recovery functionality and remaining verification in one draft. It does not announce general availability or establish a production support matrix. Confirm release availability and complete the checklist at the end before publishing.
:::

This topic describes disaster recovery for **Embedded Cluster v3 only**. It covers how application vendors package recovery infrastructure and how operators configure backups and restore an application on replacement hosts.

Embedded Cluster coordinates recovery using Velero backups. Velero stores application resources and volume backups in the configured backup location. During recovery, Embedded Cluster creates a new Kubernetes cluster, restores saved installation state, waits for replacement hosts, and restores the application through Velero.

## Requirements

* The application release must include a Velero Helm chart and the plugins and recovery infrastructure required by its backup configuration.
* The customer license must enable disaster recovery (`spec.isDisasterRecoverySupported`). The **Disaster Recovery** tab requires both this license setting and a packaged Velero chart. The `restore` command rejects licenses that do not enable disaster recovery.
* Operators must have backup storage and the credentials required by the application's Velero configuration.
* Recovery requires the **same application release and Embedded Cluster installer bundle used for the backup**, a signed license matching the application's channel, and empty replacement hosts that meet the [installation requirements](installing-embedded-requirements).
* Keep the installer bundle, Velero configuration, storage credentials, and any backup repository password accessible outside the cluster being backed up.

## Package recovery infrastructure

This section is for application vendors. Operators using an application that already includes recovery infrastructure can continue to [Configure backups](#configure-backups).

Package Velero as an application `HelmChart` or an Embedded Cluster Helm chart extension. Embedded Cluster detects Velero from the packaged chart metadata, including a Velero dependency packaged inside a wrapper chart. Renaming a Helm release to `velero` does not enable disaster recovery.

Embedded Cluster installs the entire Velero chart, including its wrapper if present, before restoring the application. Keep ordinary application workloads in separate charts. Mark other charts required during recovery with `spec.recovery: true` on an application `HelmChart`, or `recovery: true` on an Embedded Cluster extension chart entry. Chart weights control installation order.

Recovery charts can use image template functions and other template context available during bootstrap. Templates that depend on saved application configuration are unavailable until the recovery Secret is restored. Keep recovery charts independently installable with those bootstrap inputs. Recovery charts must not create active Velero schedules during restore; let operators supply schedules with their backup configuration.

The application vendor is responsible for choosing compatible Velero, chart, and plugin versions and configuring the backup method. For example:

* File-system backups require the Velero node agent and host paths that match the Embedded Cluster kubelet. With the default data directory, these paths are `/var/lib/ec/kubelet/pods` and `/var/lib/ec/kubelet/plugins`. Account for custom data directories in deployments that use them.
* Object storage requires the corresponding Velero provider plugin and credentials.
* Snapshots and snapshot data movement require the appropriate snapshot plugins, CSI components, and storage infrastructure.

Embedded Cluster does not install a fixed set of provider plugins or select a volume backup method. Validate the complete backup and restore workflow with the versions and infrastructure packaged by the application. For file-system backup requirements, see the [Velero documentation](https://velero.io/docs/v1.18/file-system-backup/).

### Include recovery metadata in backups

Embedded Cluster maintains a Secret named `embedded-cluster-recovery` in the application namespace. It contains the installation state needed to recover, including release identity, node topology, saved application configuration, license, and console password hash. It does not contain application volume data.

Every backup must include this Secret and the application's required resources and volumes. Include the application namespace and Secrets in the backup scope. Any resource filters or label selectors must also include the recovery Secret, which has this label:

```yaml
embeddedcluster.replicated.com/recovery: "true"
```

Embedded Cluster updates the Secret as installation state changes and refreshes it before a manual backup. Velero executes scheduled backups directly. Protect access to backup storage because backups contain application data and credentials.

## Define application Backup and Restore templates

This section is for application vendors. Add Velero `Backup` and `Restore` manifests to the application release alongside its other application specs. Embedded Cluster accepts one `velero.io/v1` Backup and an optional Restore. A Restore requires a Backup; multiple templates of either kind are rejected.

Embedded Cluster consumes these manifests as templates. Including them in a release does not create a live Backup or Restore during installation. Vendors define the application policy; operators configure the destination, cron expression, and retention duration.

| Template | Vendor controls | Embedded Cluster behavior |
| --- | --- | --- |
| Backup | Namespaces, resource filters, label selectors, hooks, volume options, and other native Velero backup settings | Copies the rendered `spec` into Schedule templates, using the operator's TTL and backup storage location. Manual backups use the installed policy with the selected schedule's TTL and location. |
| Restore | Restore filters, hooks, resource modifiers, and other native Velero restore settings | Saves the rendered policy in the recovery Secret and uses it for application recovery from that backup. Sets the runtime name, namespace, and selected `backupName`. |

Templates render against the installed revision's saved application configuration, license, namespace, and Embedded Cluster template context. Recovery infrastructure charts still use the limited bootstrap context described above; they cannot depend on saved application configuration.

### Example: choose the namespaces and backup method

Add a `backup.yaml` file to the application release:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: application
spec:
  includedNamespaces:
    - 'repl{{ Namespace }}'
    - application-database
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
```

The namespace template resolves to the application's installed namespace, including `kotsadm` after a v2 migration. Replace `application-database` with the additional namespace used by the application, or remove it if all workloads run in the application namespace. This example backs up resources and mounted volume contents in both namespaces using file-system backups. The packaged Velero installation must provide the corresponding node agent and plugins.

Operators do not need to repeat these settings in a Schedule. After configuring credentials and a backup storage location, they can submit:

```yaml
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: daily
  namespace: velero
spec:
  schedule: "0 2 * * *"
  template:
    storageLocation: default
    ttl: 720h
```

Embedded Cluster generates the effective template from the vendor Backup and these operator settings. Operator-supplied namespace, hook, or volume settings in the Schedule template do not override the vendor policy. Backup defaults for TTL and location apply when the corresponding Schedule settings are omitted.

Generated schedules carry the label `embeddedcluster.replicated.com/backup-policy: vendor`. Embedded Cluster periodically reconciles their templates when the installed policy changes, preserving cron, TTL, storage location, and pause state. Existing unmarked schedules are not automatically adopted; reapply them through the configuration editor to use the vendor policy. Existing backups retain their saved Restore policy.

If the release has no Backup template, operators continue to supply the full backup policy in their Schedule YAML. For supported fields and version-specific behavior, see the [Velero Backup API](https://velero.io/docs/v1.18/api-types/backup/).

### Example: use label selectors without excluding recovery state

Application data and Embedded Cluster recovery state belong in the same backup. A vendor Backup must include the application namespace and `embedded-cluster-recovery` Secret. Embedded Cluster validates this requirement and rejects policies that exclude its recovery state; it does not silently broaden the vendor's scope.

For label-based selection, use `orLabelSelectors` to include application resources and the recovery Secret. For example, the following Backup includes resources labeled `backup: application` and resources carrying the recovery label:

```yaml
apiVersion: velero.io/v1
kind: Backup
metadata:
  name: application
spec:
  includedNamespaces:
    - 'repl{{ Namespace }}'
  orLabelSelectors:
    - matchLabels:
        backup: application
    - matchLabels:
        embeddedcluster.replicated.com/recovery: "true"
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
```

Label all application resources that must be recovered, including Pods and PVCs. The recovery-label branch does not override namespace or resource exclusions: those filters must also include the recovery Secret. Do not combine `labelSelector` and `orLabelSelectors` in the same Backup.

### Example: pause an operator-managed database during restore

A resource modifier can patch a custom resource before Kubernetes receives it. This is useful when a database operator must see a restored resource in a paused state before it starts reconciling. Pod restore hooks cannot guarantee this ordering.

Add a `restore.yaml` file to the application release:

```yaml
apiVersion: velero.io/v1
kind: Restore
metadata:
  name: application
spec:
  includedNamespaces:
    - 'repl{{ Namespace }}'
    - application-database
  resourceModifier:
    kind: ConfigMap
    name: pause-postgres
```

Package the referenced ConfigMap in the Velero chart or a separate recovery chart marked `spec.recovery: true`. For example, the recovery chart can contain this manifest:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: pause-postgres
  namespace: velero
data:
  resource-modifiers.yaml: |
    version: v1
    resourceModifierRules:
      - conditions:
          groupResource: postgresclusters.postgres-operator.crunchydata.com
          resourceNameRegex: "^application-postgres$"
          namespaces:
            - application-database
        patches:
          - operation: add
            path: /spec/paused
            value: "true"
```

Replace the resource name and namespace with those used by the application's PostgresCluster. The example sets `spec.paused` to the boolean `true`. The application's database recovery procedure must then configure its data source and unpause the resource at the appropriate point.

The ConfigMap must exist in Velero's namespace before Embedded Cluster submits the application Restore. Including it only in the backup is too late. Use exactly one data key containing the rules document. Velero validates the rule syntax; Embedded Cluster checks the reference and data-key count. Test the resulting resource state: a rule matching no resources can still result in a completed restore. See [Velero resource modifiers](https://velero.io/docs/v1.18/restore-resource-modifiers/).

Embedded Cluster restores the recovery Secret first with its own restricted Restore. Vendor hooks, filters, and modifiers apply to the subsequent application Restore. If no Restore template was saved with the backup, Embedded Cluster uses its default application restore behavior.

Vendor filesystem-restore plugin settings can also be packaged in the Velero chart. Keep a single ConfigMap matching the pod-volume-restore plugin selector; Embedded Cluster rejects multiple matching ConfigMaps before starting a vendor application Restore.

### Shared packaging with KOTS and v2 upgrades

The same native Velero Backup and Restore documents can be included in an application release deployed by KOTS or Embedded Cluster v3. Validate the template functions and Velero fields against both deployment environments. Embedded Cluster v3 supports `LocalImageName` as an alias for `ReplicatedImageName` in these templates; other KOTS-only helpers are not automatically available. Include restore-hook container images in the airgap bundle and use the appropriate image template functions.

After a v2 installation is upgraded to v3, Embedded Cluster reads the vendor templates from the migrated installed revision and renders them with the migrated configuration. Include the migrated application namespace and its recovery Secret in the Backup policy. Backups taken after the upgrade contain v3 recovery state and can be restored with the matching v3 installer. Restoring a v2 backup directly into v3 is not supported. The upgrade procedure and migration of KOTS scheduling settings are outside this topic.

## Configure backups

1. Open the [persistent admin console](embedded-persistent-console). If it is not installed, run this command on a controller node:

   ```bash
   sudo ./APP_SLUG console install
   ```

   Replace `APP_SLUG` with the application slug.

1. Open **Disaster Recovery**.
1. In **Configuration**, choose **Velero YAML** and paste the configuration supplied for the application, replacing the storage settings and credentials for your environment. The prototype NFS and host-path forms are described below.
1. Click **Apply configuration**.

The editor accepts Kubernetes resource manifests, **not Helm values**. Use `---` to separate YAML documents. Each document must have `apiVersion`, `kind`, and `metadata.name`. Duplicate YAML mapping keys are rejected. For namespaced resources, omit `metadata.namespace` or set it to `velero`. Use separate documents instead of a Kubernetes `List`.

Embedded Cluster passes provider-specific configuration to Kubernetes without restricting it to a predefined storage form. Kubernetes and Velero validate the resources. Include at least one Schedule: schedules provide both automatic backups and templates for manual backups. If the release defines a Backup template, supply the cron expression, TTL, and storage location; Embedded Cluster supplies the application policy. Otherwise, include the full backup scope and volume settings in the Schedule.

The page shows **Velero is configured** when the recovery workloads, backup locations, and existing backup repositories are ready and schedules are present without validation errors. Otherwise, it displays errors and keeps the editor available. These readiness checks do not replace testing a backup and restore.

To change the configuration, click **Update configuration** and submit the updated manifests. The editor does not prefill saved credentials. Use **Cancel** to close it without applying changes.

### Example: Amazon S3 with file-system backups

This example assumes the application defines a file-system Backup template as shown above and already packages the AWS plugin and a correctly configured Velero node agent. It creates credentials, a backup location, and a daily backup schedule. It does not install Velero or its plugins.

Replace `BUCKET_NAME`, `AWS_REGION`, and the credential placeholders. Choose a prefix for this installation's backups and retain it for restore.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: cloud-credentials
  namespace: velero
type: Opaque
stringData:
  cloud: |
    [default]
    aws_access_key_id=REPLACE_ME
    aws_secret_access_key=REPLACE_ME
---
apiVersion: v1
kind: Secret
metadata:
  name: velero-repo-credentials
  namespace: velero
type: Opaque
stringData:
  repository-password: "REPLACE_WITH_A_PERSISTENT_REPOSITORY_PASSWORD"
---
apiVersion: velero.io/v1
kind: BackupStorageLocation
metadata:
  name: default
  namespace: velero
spec:
  provider: aws
  default: true
  objectStorage:
    bucket: BUCKET_NAME
    prefix: application-backups
  credential:
    name: cloud-credentials
    key: cloud
  config:
    region: AWS_REGION
---
apiVersion: velero.io/v1
kind: Schedule
metadata:
  name: daily
  namespace: velero
spec:
  schedule: "0 2 * * *"
  template:
    storageLocation: default
    ttl: 720h
```

The example sets a 30-day retention period. Namespace scope and file-system volume settings come from the application's Backup template.

For releases without a Backup template, add the application's backup scope and volume settings to `spec.template`. For example:

```yaml
template:
  includedNamespaces:
    - APP_NAMESPACE
  storageLocation: default
  ttl: 720h
  defaultVolumesToFsBackup: true
  snapshotVolumes: false
```

Replace `APP_NAMESPACE` with the application slug for a new installation or `kotsadm` for an installation migrated from v2. For required storage permissions and configuration for S3-compatible endpoints, see the [AWS plugin backup location documentation](https://github.com/velero-io/velero-plugin-for-aws/blob/main/backupstoragelocation.md). Other storage providers require their own plugins and configuration.

### Preserve the repository password

For file-system backups, `repository-password` protects access to Velero's encrypted backup repository. It does not encrypt the live PVC. Set it before the first volume backup creates the repository, store it outside the cluster, and supply the same value during recovery. Changing it after repository creation does not change the existing repository password and can make those backups inaccessible. See [Velero repository credentials](https://velero.io/docs/v1.18/file-system-backup/#prerequisites).

## NFS and host-path backup storage (prototype)

:::note
NFS backup storage for Embedded Cluster v3 is being prototyped. The configuration forms are implemented; the storage durability and recovery support matrix still require verification before production use.
:::

The configuration uses a dedicated SeaweedFS deployment to expose external NFS storage through an S3-compatible endpoint. Velero accesses that endpoint using its AWS plugin. All persistent SeaweedFS state must reside on the external storage so that a replacement instance can read the backups after the original cluster is lost.

### Configure a managed destination

In the console configuration editor or restore wizard, choose **NFS (prototype)** or **Host path (prototype)**. These modes require packaged Velero in the `velero` namespace, its AWS plugin and node agent, and no other configured backup storage location.

Supply:

| Field | Value to retain outside the cluster |
| --- | --- |
| NFS server and path | Server hostname or IP and dedicated exported directory; required for NFS mode |
| Host path | Existing absolute directory backed by an NFS mount on the controller serving the request; required for host-path mode |
| Backup prefix | DNS-style name identifying this installation's backups |
| S3 access and secret keys | Credentials for Velero's access to the dedicated SeaweedFS endpoint |
| Repository password | Persistent password used for volume backup and restore |
| Schedule | Five-field cron expression |
| Retention | Positive duration, such as `720h` for 30 days |

Embedded Cluster creates the SeaweedFS resources, credentials, backup location, and schedule. When the release defines a Backup template, the generated schedule uses that policy with the supplied cron expression and retention. The bucket is `ec-backups`; the generated backup location and schedule are named `ec-filesystem`. The dedicated SeaweedFS instance runs with one replica and the `Recreate` deployment strategy, separately from any airgap registry storage. Its internal S3 endpoint uses authenticated HTTP. All master state, volume data, and filer database files reside on the external storage; preserve the entire directory.

A new destination must be empty. Initialization writes a destination marker. During restore, supply the retained destination, prefix, credentials, and repository password. Recovery requires the existing marker and storage layout and does not initialize a missing bucket as a new destination.

Stop or fence the original backup-storage SeaweedFS instance before restoring against the same directory. `Recreate` does not prevent two separate clusters from writing concurrently.

The forms do not return saved credentials to the browser. Reenter credentials when updating configuration. Destination changes, credential rotation, and automated host-path failover are not supported by the prototype. Generated restore configuration is retained locally for resume. Headless restore continues to accept Kubernetes YAML through `--velero-config`; it does not provide an interactive NFS form.

### Prerequisites

Before configuring an NFS destination:

* Provide an external NFS server that remains available independently of the Embedded Cluster hosts. Use a dedicated export or directory for this installation's backup storage.
* Install NFS client utilities on every host eligible to run the backup SeaweedFS pod, including the first replacement controller used for recovery. Common package names are `nfs-common` on Ubuntu/Debian and `nfs-utils` on RHEL-based systems. The hosts must also have kernel support for NFS.
* Allow those hosts to reach the NFS server through the network and firewall. Required ports depend on the NFS protocol version and server configuration; the tested versions and network requirements will be documented during the prototype.
* Configure the NFS export to allow access from the eligible hosts. Grant the directory permissions required by SeaweedFS's runtime UID/GID, accounting for root squashing. The specific UID/GID will be documented after the deployment configuration is validated.
* Retain the destination configuration and Velero repository password outside the cluster so they are available during recovery.

The NFS option uses Kubernetes' built-in `nfs` volume type. Kubelet mounts the export for the pod on the host where it runs; an NFS CSI driver, pre-mounted host directory, or change to `/etc/fstab` is not required for this approach. Host NFS client utilities are still required. See [Kubernetes NFS volumes](https://kubernetes.io/docs/concepts/storage/volumes/#nfs).

### Host kernel requirements

Every host eligible to run SeaweedFS, including replacement hosts used for restore, must have NFS client support in its running Linux kernel. This applies to both the NFS and host-path options. Install the client utilities (`nfs-common` on Ubuntu/Debian or `nfs-utils` on RHEL-based systems) as well; these packages do not add missing kernel support.

For an NFSv4 server, the kernel must support the server's NFSv4 protocol version. Support can be built into the kernel or provided by loadable modules matching the running kernel. If it is modular, load it with:

```bash
sudo modprobe nfs
```

A successful mount from each eligible host is the prerequisite check. For an NFSv4.1 export, replace the server and path below with your destination:

```bash
sudo mkdir -p /mnt/nfs-check
sudo mount -t nfs -o vers=4.1 NFS_SERVER:/EXPORTED_PATH /mnt/nfs-check
findmnt /mnt/nfs-check
sudo umount /mnt/nfs-check
```

`mount.nfs: No such device` can indicate missing kernel NFS client support. If `modprobe nfs` also reports that the module is missing, inspect the running kernel configuration: `CONFIG_NFS_FS` must be enabled, with the appropriate NFS version options. A built-in driver does not require a separate module.

Some minimal VM platforms supply the kernel externally instead of booting one from the guest disk. Installing a kernel package inside those guests does not change the kernel selected by the platform. Use VMs with NFS-capable kernels or have the platform operator update the supplied kernel. A userspace NFS server such as Ganesha avoids the server's kernel NFS requirement, but does not remove the client kernel requirement on Embedded Cluster hosts.

### Authentication

The Kubernetes NFS volume configuration accepts a server, exported path, and read-only setting. It does not accept a username or password. See the [NFS volume API](https://kubernetes.io/docs/reference/kubernetes-api/core/persistent-volume-v1/#nfsvolumesource).

The initial prototype targets NFS access controlled by server export rules and filesystem UID/GID permissions. Kerberos-authenticated NFS requires additional host configuration and credentials; support for it has not been validated. See [NFS authentication options](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/managing_file_systems/mounting-nfs-shares).

NFS access controls are separate from the S3 credentials used by Velero to access SeaweedFS and from the Velero repository password.

### Existing host mounts

The **Host path (prototype)** option uses an existing NFS-backed directory. Operators are responsible for configuring that mount and making it persistent across host reboots. Embedded Cluster checks that the path is NFS-backed, and an init container checks the filesystem again before SeaweedFS starts to prevent fallback to a local directory. Embedded Cluster does not mount or unmount this operator-managed path.

SeaweedFS is pinned to the controller serving the configuration request. Prepare the mount on the first replacement controller before recovery; automatic host-path failover is not provided. A matching directory name on two hosts does not establish that both paths refer to the same storage.

### Validation still in progress

The prototype will establish the supported NFS versions and mount settings, SeaweedFS permissions and persistent directory layout, behavior after storage interruptions, and recovery using only the retained external storage. Until that testing is complete, this section is not a declaration of production support.

## Airgap packaging and registry data

Include both the EC infrastructure airgap bundle and the matching application airgap bundle. Application, extension, and recovery chart images must be available without external registry access. Use the registry image template helpers in chart values, including values for init containers and the Replicated SDK. Literal upstream image references are not automatically rewritten.

For the EC-managed registry, application image references use the stable name `registry.registry.svc.cluster.local:5000`. Embedded Cluster configures containerd on each host to route that name to the replacement registry's HTTPS endpoint. The old registry IP does not need to appear in restored Pod image references. Joining hosts receive the replacement endpoint and authentication settings. Infrastructure images needed to start Kubernetes and the registry can be loaded directly into containerd, so their Pod image names need not all use the internal registry.

Containerd can use node-level pull credentials; an application Pod does not necessarily need an `imagePullSecrets` entry. When image-pull Secrets are present, restore preserves the saved internal-registry credentials so those Secrets remain usable.

Airgap bundle validation checks application, channel, and release sequence. It does not compare each release-inventory image string with the bundle inventory. BYO registry image-access checks use rendered chart references, preserving tags, explicit digests, and tag-plus-digest references. Recovery checks infrastructure and recovery charts before metadata is available, then checks application images after importing saved configuration.

### Exclude rebuildable registry image data

Repopulate the internal registry from the matching airgap bundles during recovery. Exclude its image layers, manifests, and repository metadata from volume backups. This does not exclude Kubernetes objects, configuration, Secrets, logs, application data, or the entire registry namespace. Images pushed independently of the bundles are not recovered by this process.

Embedded Cluster labels image-data PVCs with `embeddedcluster.replicated.com/registry-image-data: "true"`. In internal-registry airgap installations, a Backup or Schedule whose scope includes `registry` or `seaweedfs` must reference a volume policy. Add this to a Backup's `spec` or a Schedule's `spec.template`:

```yaml
resourcePolicy:
  kind: ConfigMap
  name: embedded-cluster-registry-data
```

Embedded Cluster creates that ConfigMap in the Velero namespace; reference it without supplying its contents. For a custom resource-policy ConfigMap, place this rule first in `volumePolicies`, ahead of snapshot or file-system rules:

```yaml
- conditions:
    pvcLabels:
      embeddedcluster.replicated.com/registry-image-data: "true"
  action:
    type: skip
```

The exclusion covers both file-system backups and snapshots of the labeled volume contents. Submitted configurations, packaged schedules, and manual backups are checked. Policies applied directly outside Embedded Cluster must include the same rule. Application-namespace-only schedules need no additional registry policy. Keep the internal registry's SeaweedFS store dedicated to registry data; the separate NFS backup destination must retain its backup data.

## Create and manage backups

Velero runs each enabled schedule using its cron expression. In **Schedule**, pause or enable schedules as needed. Pausing a schedule stops its automatic backups; it can still serve as a template for a manual backup.

To create a manual backup:

1. In **Manual backup**, select a schedule as the backup template.
1. Review the displayed YAML. The backup uses the schedule's scope and settings, including its storage location, volume backup options, and retention period.
1. Enter a backup name, or leave it blank for an automatically generated name.
1. Click **Create backup**.
1. Watch the **Backups** table until the backup reaches its final status. A request being accepted does not mean that the backup has completed.

The table shows backups with the latest first, including failed and partially failed backups. After configuration, existing backups in the storage location can take time to appear while Velero synchronizes them. The page updates automatically and shows backup-location synchronization status below the table.

To delete a backup, click **Delete** on its row and confirm in the dialog. This requests deletion through Velero, including the backup's stored data; it does not merely hide the row. Deletion can take time or fail if the storage location does not permit deletion.

### Check volume backup completion

A backed-up PVC resource alone does not confirm that its volume contents were backed up. For file-system backups, inspect the PodVolumeBackup resources associated with the backup. From a shell with access to the cluster's `kubectl`, run:

```bash
kubectl -n velero get podvolumebackups.velero.io \
  -l velero.io/backup-name=BACKUP_NAME -o yaml
```

Replace `BACKUP_NAME` with the name from the console. Check that the expected volumes are present and their `status.phase` is `Completed`. Applications without eligible mounted volumes might have no PodVolumeBackup resources. Snapshot-based backups use different resources; follow the application's storage-specific verification instructions.

## Restore on replacement hosts

Restore creates a new cluster. Do not install the application on the replacement hosts before running restore. Embedded Cluster installs Kubernetes and recovery infrastructure first, leaving application workloads for Velero to restore.

### Start recovery

1. Download and extract the installer bundle matching the backed-up application release and Embedded Cluster version onto the first replacement controller. Keep the extracted `assets` directory alongside the application binary.
1. Copy the signed license to that host.
1. Run:

   ```bash
   sudo ./APP_SLUG restore --license ./license.yaml
   ```

1. Set the restore UI password and configure TLS when prompted.
1. Open the URL printed by the command and sign in using the restore UI password. Leave the command running while using the wizard.

Embedded Cluster runs host preflight checks before installing Kubernetes. The `--ignore-host-preflights` option bypasses non-strict failures only; strict failures and errors executing the checks still stop recovery.

The bootstrap license must enable disaster recovery and match the installer application and channel. Its license ID does not have to match the backed-up license ID. The saved license is recovered with the installation state.

### Configure Velero and select a backup

1. Supply compatible Velero configuration, including the same storage bucket, prefix, and repository password used for the backup. Storage credentials must permit access to that backup.
1. Apply the configuration and wait for Velero to synchronize its backup list.
1. Select a backup with status **Completed**.

You can reuse configuration containing Schedule resources. Embedded Cluster automatically pauses submitted schedules during recovery. They remain paused until you explicitly enable them after recovery.

Embedded Cluster first restores only the recovery Secret. It checks the installation namespace and `kotsadm`, the namespace used by v2-migrated installations, and requires exactly one matching recovery Secret. It validates the saved release identity and then uses the recovered application namespace, topology, and configuration. No namespace argument is needed.

The bootstrap controller automatically receives the first saved controller role set. Restore does not accept `--roles`; additional hosts use the role combinations shown in the join instructions.

### Recover installation settings

The recovery Secret contains the configured CIDR, effective pod/service CIDRs, resolved data directory, and daemon API port. Omit the corresponding flags to recover those settings automatically. Explicit values override the backup.

| Option | Restore behavior |
| --- | --- |
| `--cidr` | Use the saved network unless explicitly overridden. Supply a conflict-free CIDR at startup if the default bootstrap network conflicts with the replacement environment. |
| `--data-dir` | Use the saved directory unless explicitly overridden. The flag takes a parent directory; Embedded Cluster appends the application slug once. `EC_DATA_DIR` supplies the initial bootstrap default, not an override of the saved directory. |
| `--api-port` | Use the saved daemon API port unless explicitly overridden. A port-only change restarts the EC daemon without rebuilding Kubernetes. |
| `--network-interface` | Use the supplied interface or detect one on the replacement host. Do not recover the old interface name. Joining hosts can supply their own interface. |
| `--http-proxy`, `--https-proxy`, `--no-proxy` | Supply the replacement environment's settings. Saved proxy values are not adopted. Automatic exclusions are recalculated for the final networks. Proxy flags cannot be used with airgap recovery. |
| `--hostname`, `--tls-cert`, `--tls-key` | Configure the replacement interface and TLS; supply certificate and key together or use the self-signed flow. Saved console hostname and certificates are not adopted. |
| `--installer-port`, `--installer-password` | Configure this recovery session. The port defaults to `30080`; the final console recovers the saved password hash. |
| `--headless`, `--yes`, `--ignore-host-preflights` | Apply only to this invocation. Headless mode and preflight bypasses are not recovered from backup or inherited on resume. |
| `--restore-timeout`, `--topology-timeout` | Limit each Velero restore phase and the wait for replacement hosts; defaults are four and 24 hours, respectively. |

Saved application configuration is restored without a `--config-values` argument. Recovery does not install application updates. Release-provided overrides and worker profiles remain part of the recovered configuration; CIDR customization through unsupported k0s overrides is not supported by this workflow.

Because Velero needs Kubernetes before it can retrieve metadata, restore initially uses bootstrap defaults or supplied values. If the recovered network or data directory differs, the same restore process keeps metadata in memory, resets the bootstrap cluster, and reinstalls Kubernetes and recovery infrastructure once with both final settings. This happens before other nodes join or application resources and volume data are restored. Keep the process running and the installer assets accessible throughout the rebuild. Matching settings require no rebuild.

### Airgap recovery

Place the matching bundles alongside the installer in the same layout used for installation, then run:

```bash
sudo ./APP_SLUG restore --license ./license.yaml --airgap \
  --velero-config ./velero.yaml
```

With the internal registry, restore first loads the EC infrastructure images, starts local storage and a single-node registry, and loads application and recovery images before starting Velero. After retrieving metadata, it restores registry credentials while retaining the replacement endpoint. Once the saved topology is ready, it migrates the internal registry to high availability when at least three controllers are required. Required images remain available through that transition. Application resource and volume recovery follows.

The supplied airgap mode must match the backup. Airgap mode is retained on resume. Retain both bundles outside the cluster; a backup does not replace them.

### Bring your own registry

Supply the registry address and the authentication and trust settings needed before Velero starts. For example, for an airgap registry using a private CA:

```bash
sudo ./APP_SLUG restore --license ./license.yaml --airgap \
  --velero-config ./velero.yaml \
  --registry registry.example.com/application \
  --registry-username REGISTRY_USER \
  --registry-password REGISTRY_PASSWORD \
  --registry-ca-cert ./registry-ca.crt
```

Use `--registry-tls-cert` and `--registry-tls-key` together if client authentication is required. Anonymous registries need no username or password; standard trusted certificates need no custom CA. BYO registry access uses verified HTTPS; HTTP is not supported.

Airgap install and restore upload infrastructure, application, and extension images from the matching bundles without requiring external image-copying tools. Credentials must permit those uploads as well as pulls. Online recovery requires the images to be present already. BYO recovery skips the EC-managed registry and its HA migration.

After metadata recovery, Embedded Cluster also checks the backed-up registry credentials needed for restored image references. Invalid access stops recovery. A registry address or namespace-path mismatch produces a warning but does not itself stop recovery. Restored images still refer to the original registry; the warning is not an automatic image-reference rewrite. Keep that registry accessible to restored workloads.

### Join replacement hosts

For a multi-node backup, the restore wizard displays the required role combinations and host counts alongside the joined hosts. The first controller is already running; do not join it again.

1. In **Add Hosts**, select the roles for the replacement host.
1. On that replacement host, run the displayed `curl` command to download its join bundle.
1. Run the displayed `tar` command to extract the bundle.
1. Run the displayed `node join` command from the extracted directory.
1. Repeat for the remaining hosts. Join controller nodes one at a time.

The download creates a bundle for the selected roles; there is no separate generation step. The replacement hosts must be able to reach the first controller at the address shown in the download command.

The wizard warns if the selected role combination does not match the backup or is already satisfied. Recovery continues automatically when the joined hosts match the saved counts and all required hosts are ready and running the matching release.

The replacement cluster can use different network interfaces and pod/service CIDRs. Configure them with `--network-interface` and `--cidr` when starting recovery if necessary. Joining hosts receive the replacement cluster's network settings. Application settings containing old addresses might still require application-specific changes.

### Complete recovery and enable schedules

After the hosts and storage infrastructure are ready, Embedded Cluster restores application resources and volumes through Velero using the Restore policy saved in the backup, if present, then reconciles the matching application release. Failed or partially failed restores do not mark recovery complete.

On **Enable backup schedules**, enable the schedules you want to run. If you configured a backup location as `ReadOnly` during recovery, change it to `ReadWrite` before resuming backups.

The restore command keeps serving the UI after recovery completes. Press **Ctrl+C** when you are finished. You can also manage schedules later from **Disaster Recovery** in the persistent admin console. Install the console on a recovered controller with `sudo ./APP_SLUG console install` if needed. The recovered installation uses the console password saved in the backup.

### Resume an interrupted restore

On the first replacement controller, run:

```bash
sudo ./APP_SLUG restore --resume --license ./license.yaml
```

The license is required on every invocation, including resume. Repeat `--headless` and any invocation-specific preflight bypass when needed. Previously resolved persistent settings are retained; conflicting replacement settings are rejected. Embedded Cluster uses the saved recovery progress and Velero Restore names to continue. Failed Velero restore attempts can be retried. Interactive recovery writes progress to `restore.log` after printing the UI URL.

Before installation state is imported, a different `--backup` or `--velero-config` can change the selection after the previous metadata restore reaches a terminal status. Repeating the same inputs preserves existing restore attempts.

If interrupted after the bootstrap cluster is reset and before the recovery Secret is available again, fully reset the replacement host and restart recovery. Automatic resume across that rebuild gap is not supported.

### Restore without the browser

To supply configuration and a backup name from the command line:

```bash
chmod 600 ./velero.yaml
sudo ./APP_SLUG restore --license ./license.yaml \
  --headless --yes \
  --velero-config ./velero.yaml \
  --backup BACKUP_NAME
```

Omit `--backup` for an interactive numbered list after synchronization. It lists newest backups first, with status and error counts; only completed backups without errors can be selected. Enter `q` to cancel. `--yes` does not select a backup automatically. Supply `--backup` for unattended selection and all other inputs needed to avoid prompts.

For multiple hosts, the terminal displays `curl`, `tar`, and `node join` commands for each saved role combination, excluding the first controller already running. Bundles are generated when downloaded from a token-authenticated, TLS-pinned endpoint on the first controller's internal address and installer port. Replacement hosts must be able to reach it; use the generated commands as printed. No browser is needed. Role counts and node status update in the terminal, and restore continues automatically when the topology is ready. Redirected output omits terminal control sequences.

The download endpoint closes once the required topology is ready or the command exits. Headless recovery exits after completion. Enable paused schedules later from the admin console.

Run `sudo ./APP_SLUG restore --help` for the full list of options. The application namespace and first controller roles are recovered automatically; `--app-namespace` and `--roles` are not restore options.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| The Disaster Recovery tab is missing | Confirm that the installed license enables disaster recovery and the deployed release packages a Velero chart. |
| Configuration is unhealthy | Read the displayed error. Check recovery workload readiness, backup storage access, repository readiness, and Schedule validation errors. Missing schedules are configuration errors. |
| Existing backups are not listed | Check the synchronization status under the table, the configured bucket and prefix, storage access, and whether backup synchronization is disabled for a location. |
| A backup is partially failed or failed | Inspect its errors and the Velero logs before attempting recovery. Recovery requires a completed backup. |
| Volume recovery cannot access the repository | Confirm that the supplied repository password matches the password used when the repository was created, and check storage credentials. |
| Recovery is waiting for hosts | Compare joined hosts and roles with the expected topology. Check node readiness and release versions, and remove extra hosts if counts exceed the backup. |
| The installer does not match the backup | Use the original application release and Embedded Cluster installer bundle. Recovery is not an application upgrade. |
