# Run host preflight checks before installation

Standalone host preflight checks require Embedded Cluster `VERSION_PLACEHOLDER` or later.

Run standalone host preflight checks to evaluate a host before installation or a planned change window. Use them to validate hosts in provisioning automation, check a node before it joins, or check readiness again after changing host settings.

The commands run Embedded Cluster's built-in host checks and any vendor-provided host checks. They do not install Embedded Cluster, start its services, or configure the host. Checks can create temporary files, generate disk I/O, and test network connectivity. The command removes temporary workspaces when it finishes.

Standalone commands do not run application preflight checks. Installation and joining still run their own host checks afterward.

## Before you begin

* Use the application package for the v3 release you intend to install. For a joining node, use a join bundle from the destination cluster.
* Run the command as root on the host you want to check.
* Mount the volumes you intend to use before running checks. If the data directory does not exist, the disk benchmark creates a temporary directory inside its nearest existing ancestor. Results describe that filesystem, not a volume mounted later.
* Install the host tools required for disk checks. For more information about `fio`, see [Disk performance checks](installing-embedded-requirements#disk-performance-checks) in _Embedded Cluster installation requirements_.

Replace `APP_SLUG` in the examples with the name of the application binary.

## Check a host before installing

1. Download and extract the target application package using your vendor's [online](installing-embedded) or [air gap](installing-embedded-air-gap) instructions. Stop before running `install`.

1. From the extracted package directory, run:

   ```bash
   sudo ./APP_SLUG install run-preflights
   ```

1. If you intend to change the default installation settings, supply the same settings to the check. For example:

   ```bash
   sudo ./APP_SLUG install run-preflights \
     --data-dir /mnt/embedded-cluster \
     --network-interface eth0 \
     --cidr 10.244.0.0/16
   ```

   Choose a CIDR appropriate for your network. Add `--airgap` when checking an air gap installation.

   Use `--http-proxy`, `--https-proxy`, and `--no-proxy` to match your proxy settings. Outside air gap mode, unset proxy flags fall back to the corresponding lowercase or uppercase environment variables. Explicit flags take precedence.

   An optional `--license /path/to/license.yaml` supplies custom endpoints. When using `--registry`, also supply `--license` and any intended `--config-values` file so image checks use the correct chart configuration. The command accepts the registry credentials and certificate flags listed in [install](embedded-cluster-install).

1. Review the results and address failed checks before installation. To list the supported flags, run:

   ```bash
   sudo ./APP_SLUG install run-preflights --help
   ```

## Check a node before joining

1. Obtain a join bundle for the intended node roles from the destination cluster. Copy or download it to the node and extract it. See [Join nodes](embedded-manage-nodes#add-nodes).

1. From the extracted join bundle directory, run:

   ```bash
   sudo ./APP_SLUG node join run-preflights
   ```

   `join run-preflights` is an equivalent command. To select a network interface, add `--network-interface eth0`.

1. Review the results before running the normal `node join` command. The checks use the bundle's roles and cluster settings. Bundles that retrieve a join profile require access to the destination cluster and a valid join token. Obtain a new bundle if the token expires.

The v3 command reads its inputs from the join bundle. It does not accept the two positional arguments used by the v2 `join run-preflights` command. Update existing scripts accordingly.

## Read results in automation

Use `--format json` with either command to write the result object to stdout. Notices and human-readable output go to stderr. For example:

```bash
sudo ./APP_SLUG install run-preflights --format json > host-preflights.json
```

The JSON result uses these fields:

| Field | Description |
|-------|-------------|
| `pass` | Passed checks. |
| `warn` | Warnings, including checks that could not fully evaluate the host. |
| `fail` | Failed checks. |
| `error` | An execution error, when present. |

Each check contains a `title` and `message`. It can also contain `source` and `strict` fields. Check lists can be `null` when empty.

Failed checks and execution errors return a nonzero exit status. Warnings alone do not. Inspect warnings and confirm that the checks your automation requires are present, rather than relying only on the exit status. Argument or initialization errors can occur before a JSON result is available.

## Understand the results

Results are point-in-time, not a guarantee of a later install or join. Disk load, network access, and available resources can change between the check and installation.

Standalone checks inspect the host without applying the host configuration that installation normally performs. For example, a kernel parameter check can fail for a setting that installation attempts to configure. If installation directories do not exist, the command cannot check their SELinux labels and reports a warning.

### Check a host that already runs a cluster

You can run the target application's host checks while a cluster is running. For example, check each host before upgrading from Embedded Cluster v2. Downloading the package and running `install run-preflights` does not begin installation or upgrade the existing cluster.

A running cluster can occupy required ports or consume resources, causing some host checks to fail. Disk benchmarks also compete with existing workloads. Review each failure to determine its cause. Do not assume the running cluster causes every failure. Checks such as cgroup mode can reveal host requirements that you must address before installation or upgrade.

For more information about v2 upgrade requirements, see [Upgrade from Embedded Cluster v2](embedded-v3-migrate).
