## cgroup v2 {#cgroup-v2}

Embedded Cluster v3 runs Kubernetes 1.35 or later, which requires cgroup v2 and a Linux kernel of 4.5 or later. The host preflight checks fail on a host that uses cgroup v1.

Most current distributions use cgroup v2 by default, including RHEL 9 and later, Ubuntu 22.04 and later, and Debian 12 and later. RHEL 8 and other Enterprise Linux 8 distributions, such as Rocky Linux 8, AlmaLinux 8, and Oracle Linux 8, use cgroup v1 by default. You can switch these hosts to cgroup v2. Ubuntu 20.04 also uses cgroup v1 by default and has reached the end of standard support, so move those hosts to Ubuntu 22.04 or later. Hosts with a kernel older than 4.5, such as RHEL 7, can't use cgroup v2.

To check which version a host uses, run:

```bash
stat -fc %T /sys/fs/cgroup/
```

The command returns `cgroup2fs` for cgroup v2 and `tmpfs` for cgroup v1.

To switch an Enterprise Linux 8 host to cgroup v2:

1. Add the `systemd.unified_cgroup_hierarchy=1` kernel argument:

    ```bash
    sudo grubby --update-kernel=ALL --args="systemd.unified_cgroup_hierarchy=1"
    ```

1. Reboot the host.

1. Run the `stat` command again and confirm that it returns `cgroup2fs`.

On a multi-node cluster, switch every node, and reboot one node at a time.

## Unix accounts for Kubernetes components

During installation, Embedded Cluster automatically creates the following Unix accounts, which internal Kubernetes components require:

* **etcd**: Used by the Kubernetes etcd database, which stores cluster state.
* **konnectivity-server**: Used by the Konnectivity service, which facilitates secure communication between internal components.
* **kube-apiserver**: Used by the Kubernetes API server.
* **kube-scheduler**: Used by the Kubernetes scheduler to schedule workloads such as pods.

You do not need to take any action to create these roles. Removing them will make the cluster non-functional.

For more information about the internal Kubernetes components, see [Kubernetes Components](https://kubernetes.io/docs/concepts/overview/components/) in the Kubernetes documentation.

For more information about the Konnectivity service, see [Set up Konnectivity service](https://kubernetes.io/docs/tasks/extend-kubernetes/setup-konnectivity/) in the Kubernetes documentation.

## About firewalld configuration

When Firewalld runs in the installation environment, Embedded Cluster modifies the Firewalld config to allow traffic over the pod and service networks. It also opens ports 2380, 6443, 9443, and 10250/TCP and port 4789/UDP. Embedded Cluster does not open the console and API port (30000/TCP by default) or ports 9091, 10249, and 10256/TCP. Create firewall openings for those ports yourself. See [Port requirements](#port-requirements).

Embedded Cluster adds the following rule to Firewalld:

```xml
<?xml version="1.0" encoding="utf-8"?>
<zone target="ACCEPT">
  <interface name="cali+"/>
  <interface name="tunl+"/>
  <interface name="vxlan-v6.calico"/>
  <interface name="vxlan.calico"/>
  <interface name="wg-v6.cali"/>
  <interface name="wireguard.cali"/>
  <source address="[pod-network-cidr]"/>
  <source address="[service-network-cidr]"/>
</zone>
```

## Secrets at rest {#secrets}

Limit root and `sudo` access on each host to the people who administer the application, and restrict access to backup storage. Anyone with root access to a host can read every secret on it, along with the application's data.

Secrets on the hosts and in backups are not encrypted at rest. On a single host, the encryption key would have to be stored on that same host, so encryption would not keep secrets from anyone with root access. If your security policy requires encryption at rest, use disk encryption on the hosts and the storage provider's encryption for backups.

Secrets include the license, the application's configuration values (including generated passwords), registry and proxy credentials, the admin console password hash, and TLS private keys.

In this section, `DATA_DIR` is the Embedded Cluster data directory. The default is `/var/lib/APP_SLUG`. You can change it with the `--data-dir` flag of the [install command](embedded-cluster-install).

### Kubernetes Secrets

Embedded Cluster keeps most secrets in Kubernetes Secrets, including the license, the application's configuration values and the values used for each earlier deployment, registry and proxy credentials, and the admin console credentials. Kubernetes stores Secrets in its datastore on controller nodes, under `DATA_DIR/k0s`. Embedded Cluster does not configure Kubernetes encryption at rest for Secrets. For more information, see [Encrypting Confidential Data at Rest](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/) in the Kubernetes documentation.

### Files that Embedded Cluster writes on the host

Some secrets are also kept in files on the host, so that components can use them when Kubernetes isn't running. Starting in 3.20.0, Embedded Cluster makes these files readable only by root:

* `DATA_DIR` on controller nodes holds the admin console password hash and the key that signs Embedded Cluster API tokens, so that you can log in to the admin console when Kubernetes isn't running. `DATA_DIR/support` holds a copy of the application's support bundle redaction rules, which can include sensitive values.
* `/etc/embedded-cluster` holds the admin console TLS private key on controller nodes, and the node's own TLS private key on worker nodes.
* `/etc/k0s/containerd.d` holds the registry credentials that the container runtime uses to pull images: `registry-auth.toml` for the Replicated registry and proxy registry, `byo-registry-auth.toml` for a registry you provide, and `embedded-registry.toml` for the air gap registry. `/etc/k0s/containerd/certs.d` holds the TLS client key for a registry you provide, if you configured one.
* `/etc/systemd/system` holds `http-proxy.conf` drop-in files for the Embedded Cluster and Kubernetes services. They contain proxy URLs, including proxy credentials if you configured them.
* `DATA_DIR/tmp` holds temporary files, such as the restore settings during a restore. Embedded Cluster deletes them when it finishes, and removes any that are left behind the next time it starts.

During installation, before Kubernetes is running, Embedded Cluster keeps the license and configuration values in `DATA_DIR/revisions`. It deletes these files after it saves the values in Kubernetes Secrets.

Embedded Cluster does not delete files that you provide, such as the license file or a configuration values file that you pass to the install command. Delete these files or restrict access to them after installation.

### Files left on a node after it joins or upgrades

To add or upgrade a node, you run commands on the node that download a `.tar.gz` file into the current directory and extract it. Join and upgrade bundles contain the Embedded Cluster binaries and installation settings that aren't secret. A join bundle also contains a token that lets a host join the cluster with the roles you selected. Starting in 3.20.0, the token expires after one hour by default. In earlier versions, the default is 24 hours. The joining node uses the token to get the credentials it needs from the cluster.

Join bundles that the Embedded Cluster CLI creates with `create-join-bundle` can be read only by root. A bundle you download with the `curl` command gets your default file permissions, so restrict access to it until the join token expires.

When `node join` or `node upgrade` succeeds, it removes the files it extracted, but not the `.tar.gz` file. Delete the `.tar.gz` file after the node joins or upgrades.

### Backups

When disaster recovery is configured, backups include Kubernetes Secrets, both the application's own Secrets and the Secrets that Embedded Cluster uses to restore the installation. Those hold the license, the application's configuration values, the admin console password hash and TLS private key, and installation settings, including registry and proxy credentials. For file-system backups, the repository password protects the volume data in the backup repository. It does not protect the Kubernetes resources, so these Secrets are stored in the backup storage without encryption. Restrict access to the backup storage, and use the storage provider's encryption if your security policy requires backups to be encrypted. For more information about the repository password, see [Preserve the repository password](embedded-disaster-recovery-v3#preserve-the-repository-password) in _Back up and restore Embedded Cluster v3_.
