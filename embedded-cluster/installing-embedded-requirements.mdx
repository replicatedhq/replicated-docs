## cgroup v2 {#cgroup-v2}

Embedded Cluster v3 runs Kubernetes 1.35 or later, which requires cgroup v2 and a Linux kernel of 4.5 or later. The host preflight checks fail on a host that uses cgroup v1.

Most current distributions use cgroup v2 by default, including RHEL 9 and later, Ubuntu 22.04 and later, and Debian 12 and later. RHEL 8 and other Enterprise Linux 8 distributions, such as Rocky Linux 8, AlmaLinux 8, and Oracle Linux 8, use cgroup v1 by default. You can switch these hosts to cgroup v2. Ubuntu 20.04 also uses cgroup v1 by default and has reached the end of standard support, so move those hosts to Ubuntu 22.04 or later. Hosts with a kernel older than 4.5, such as RHEL 7, can't use cgroup v2.

To check which version a host uses, run:

```bash
stat -fc %T /sys/fs/cgroup/
```

The command returns `cgroup2fs` for cgroup v2 and `tmpfs` for cgroup v1.

To switch an Enterprise Linux 8 host to cgroup v2:

1. Add the `systemd.unified_cgroup_hierarchy=1` kernel argument:

    ```bash
    sudo grubby --update-kernel=ALL --args="systemd.unified_cgroup_hierarchy=1"
    ```

1. Reboot the host.

1. Run the `stat` command again and confirm that it returns `cgroup2fs`.

On a multi-node cluster, switch every node, and reboot one node at a time.

## Unix accounts for Kubernetes components

During installation, Embedded Cluster automatically creates the following Unix accounts, which internal Kubernetes components require:

* **etcd**: Used by the Kubernetes etcd database, which stores cluster state.
* **konnectivity-server**: Used by the Konnectivity service, which facilitates secure communication between internal components.
* **kube-apiserver**: Used by the Kubernetes API server.
* **kube-scheduler**: Used by the Kubernetes scheduler to schedule workloads such as pods.

You do not need to take any action to create these roles. Removing them will make the cluster non-functional.

For more information about the internal Kubernetes components, see [Kubernetes Components](https://kubernetes.io/docs/concepts/overview/components/) in the Kubernetes documentation.

For more information about the Konnectivity service, see [Set up Konnectivity service](https://kubernetes.io/docs/tasks/extend-kubernetes/setup-konnectivity/) in the Kubernetes documentation.

## About firewalld configuration

When Firewalld runs in the installation environment, Embedded Cluster modifies the Firewalld config to allow traffic over the pod and service networks. It also opens ports 2380, 6443, 9443, and 10250/TCP and port 4789/UDP. Embedded Cluster does not open the console and API port (30000/TCP by default) or ports 9091, 10249, and 10256/TCP. Create firewall openings for those ports yourself. See [Port requirements](#port-requirements).

Embedded Cluster adds the following rule to Firewalld:

```xml
<?xml version="1.0" encoding="utf-8"?>
<zone target="ACCEPT">
  <interface name="cali+"/>
  <interface name="tunl+"/>
  <interface name="vxlan-v6.calico"/>
  <interface name="vxlan.calico"/>
  <interface name="wg-v6.cali"/>
  <interface name="wireguard.cali"/>
  <source address="[pod-network-cidr]"/>
  <source address="[service-network-cidr]"/>
</zone>
```

## Secrets on the host {#secrets}

Embedded Cluster does not encrypt application secrets at rest. On a single host, the encryption key would have to be stored on that same host, where anyone with root access could read it and decrypt the secrets. Encryption at rest would not keep secrets from anyone who can already read them.

The security boundary for secrets is root access to the host. Embedded Cluster restricts the files that hold secrets so that users without root access cannot read them. Anyone with root access can read every secret on the host, along with the application's data. Limit root and `sudo` access on each host to the people who administer the application.

Secrets include the license, the application's configuration values (including generated passwords), registry credentials, and TLS private keys. Embedded Cluster stores them in the following locations on each host:

* The Kubernetes datastore under `DATA_DIR/k0s`, which holds Kubernetes Secrets. After installation, Embedded Cluster keeps the application's configuration values in Secrets, including the values used for each earlier deployment.
* `/etc/embedded-cluster`, which holds installation settings, including registry credentials and the admin console TLS private key.
* `DATA_DIR`, which holds the admin console password hash and the key that signs Embedded Cluster API tokens.
* `DATA_DIR/revisions`, which holds the license and the configuration values that Embedded Cluster saved during installation, before Kubernetes was running.

In this list, `DATA_DIR` is the Embedded Cluster data directory.

### Files left on a node after it joins or upgrades

To add a node, you run commands on the new node that download a `.tar.gz` file and extract it. The file contains the license, the application's configuration values, the admin console password hash and TLS private key, the key that signs Embedded Cluster API tokens, installation settings including registry credentials, and a token for joining the cluster. The `.tar.gz` file used to upgrade a node with `node upgrade` contains the same secrets, except the join token.

Bundles that the Embedded Cluster CLI creates with `create-join-bundle` or `create-upgrade-bundle` can be read only by root. A bundle you download with the `curl` command gets your default file permissions, so restrict access to it until you delete it.

When `node join` or `node upgrade` succeeds, it removes the files it extracted, but not the `.tar.gz` file. Delete the `.tar.gz` file after the node joins or upgrades. If the command fails, also delete the extracted `assets` directory once you no longer need to retry.

### Backups

When disaster recovery is configured, backups include Kubernetes Secrets, both the application's own Secrets and the Secrets that Embedded Cluster uses to restore the installation. Those hold the license, the application's configuration values, the admin console password hash, and installation settings. The repository password encrypts the volume data in a backup, but not the Kubernetes resources, so these Secrets are stored in the backup storage without encryption. Restrict access to the backup storage, and use the storage provider's encryption if your security policy requires backups to be encrypted. For more information about the repository password, see [Preserve the repository password](embedded-disaster-recovery-v3#preserve-the-repository-password) in _Back up and restore Embedded Cluster v3_.
