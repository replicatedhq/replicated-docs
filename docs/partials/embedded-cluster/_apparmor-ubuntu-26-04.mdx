On Ubuntu 26.04 hosts with recent kernels, such as `7.0.0-43-generic` and `7.0.0-1017-aws`, AppArmor denies signals between processes in the same container. Applications that rely on these signals can stop responding or fail to shut down. For example, PostgreSQL pods can hang until the database reaches its connection limit. The kernel log on the host shows `apparmor="DENIED" operation="signal"` entries with a `peer` that ends in `//&unconfined`.

Recent Ubuntu 26.04 kernels, starting with `7.0.0-42-generic`, add a stacked AppArmor label to container processes. This happens when the `kernel.apparmor_restrict_unprivileged_unconfined` setting is `1`, which is the Ubuntu default. Embedded Cluster runs containers with the default AppArmor profile in containerd. This profile predates the change and does not allow signals to processes with the stacked label. containerd updated the profile to allow them. For more information, see [containerd issue #14485](https://github.com/containerd/containerd/issues/14485) in the _containerd_ repository and [bug #2172640](https://bugs.launchpad.net/ubuntu/+source/linux/+bug/2172640) in _Launchpad_, which reports the kernel change. The updated profile applies to the following Embedded Cluster versions:

* **Kubernetes 1.35 and earlier:** These versions use containerd 1.7, which is end of life and does not receive the updated profile. To run these versions, use Ubuntu 24.04 hosts.
* **Kubernetes 1.36 and later:** These versions use containerd 2.3. The updated profile will be available in a future Embedded Cluster release after it is available in containerd and k0s.

Until a release with the updated profile is available, use Ubuntu 24.04 hosts, or keep Ubuntu 26.04 hosts on an earlier kernel, such as `7.0.0-38-generic`.
