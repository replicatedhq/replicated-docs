The `builder` key has the following requirements and recommendations:
* Replicated recommends that you include only the minimum Helm values in the `builder` key required to template the Helm chart with the correct image tags.
* Use only static, or _hardcoded_, values in the `builder` key. You can't use template functions in the `builder` key because values in the `builder` key are not rendered in a customer environment.
* Any `required` Helm values that need to be set to render the chart templates must have a value in the `builder` key. For more information about the Helm `required` function, see [Using the 'required' function](https://helm.sh/docs/howto/charts_tips_and_tricks/#using-the-required-function) in the Helm documentation.
* Specify `kubeVersion` in the root Helm chart. The Vendor Portal renders Helm charts with the minimum Kubernetes minor version that satisfies the `kubeVersion` in the root Helm chart. For example, if the chart specifies `kubeVersion: >=1.24.1`, then it's rendered with Kubernetes 1.25.0. If this fails or if a `kubeVersion` is not specified in the root Helm chart, then the Vendor Portal attempts to render the chart with each supported minor version of Kubernetes up to the latest version.
* Every conditional template that uses a unique image must render with the values in the `builder` key. For example, if a self-signed certificate Job renders only when `tls.mode` is `self-signed`, set `tls.mode: self-signed` in the `builder` key. This makes the template render so that the Vendor Portal includes its image.
* The Vendor Portal renders the chart with a single set of values: the chart's default values plus the values in the `builder` key. It ignores the `values` and `optionalValues` keys when it builds the image list, so a value set only in `values` does not cause a conditional template to render.
* If two templates are mutually exclusive, such as the two branches of an `if`/`else` on the same value, they can't both render in a single pass. Set the `builder` key to render one branch, and list the images from the other branch in the `additionalImages` field of the Application custom resource. For more information about when to use `additionalImages`, see [When to use additionalImages](/vendor/operator-defining-additional-images#when-to-use-additionalimages) in _Define additional images_.
* If the `builder` values don't render an image and `additionalImages` doesn't list it, the Vendor Portal omits the image from the release's image list. The release still builds successfully, and the Vendor Portal doesn't show a warning. When a customer enables the feature that uses the image, the Pods for that feature fail to start with an image pull error. This affects air gap installations and installations where the customer pushes images to their own registry.
